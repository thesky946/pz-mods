# Надёжность изменений — обязательный порядок

- Перед исправлением воспроизвести дефект тестом, который падает на текущем коде. Проверять результат в игровом состоянии, а не только отсутствие исключений или сообщение «готово».
- Для каждого изменённого игрового шага проверить успех, отказ до старта, отмену, исчезновение предмета, нехватку места, повторный callback и устаревший callback после завершения сессии.
- Сверять используемые сигнатуры и ограничения с установленным vanilla Lua/Java API. Моки должны повторять контракт игры: перенос может не состояться, посуда может замениться новым объектом, короткий и полный тип различаются.
- Перед переходом к следующему шагу проверять его фактическое условие: предмет в нужном контейнере, вода набрана, плита включена и нагревает, блюдо действительно приготовлено. Не считать callback доказательством успеха.
- Ошибки и отмена проходят единый путь завершения; не оставлять активную сессию без ожидаемого действия и включённую модом плиту без контроля. Не повторять расходующее продукты действие после неизвестного результата.
- Проверять смежные сценарии: пол и сумки, другая еда на плите, заранее включённая плита, заморозка, ускорение и пауза, изменение плана перед запуском, повторное открытие окна.
- До синхронизации и публикации запускать `tools/check.ps1 -Mod <slug>`. Не менять тестовые ожидания только ради зелёного результата: каждое изменение ожидания должно соответствовать обоснованному изменению поведения.
- Проверять целостность всей серии правок до отправки в работающую игру; использовать один watcher на bridge. После изменений контрактов состояния и обработчиков событий не обещать надёжную миграцию существующей сессии через reload.
- В финале разделять: что исправлено, что проверено автоматическими тестами, что реально проверено в игре и что ещё не подтверждено. Не обещать отсутствие багов на основании только моков или RELOAD ACK.

When the user asks to publish or release a new version to Steam, run:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\publish_workshop.ps1 -Mod cook-it-for-me
```

This builds `mods/cook-it-for-me` and updates Workshop item `3801601464` using its `mod-manifest.json`. An explicit publishing request authorizes the upload; do not ask for redundant confirmation.

- Steam must be running and signed into the owning account.
- Use `-PatchNote '...'` for release notes supplied by the user.
- Use `-DryRun` to build and validate without uploading.
- Report success only after the uploader succeeds. Report errors without claiming publication.
- For repository context, read `CODEX.md`.

# Forge Live watcher: проверка изменений без перезапуска

- В проекте используется Forge Live watcher (`tools/watch.cmd <slug>`). Изменения существующих Lua-модулей в `mods/<slug>/42/` поддерживают hot reload вместе с зависимыми модулями. Не советовать перезапуск игры по умолчанию после таких правок.
- Перед рекомендацией перезапуска проверить работающий watcher и свежие подтверждения `RELOAD ACK` / `[ForgeLive] reloaded` для изменённых файлов, а также ошибки в `%USERPROFILE%/Zomboid/console.txt`. Старый лог или само наличие процесса не доказывают применение последних правок.
- После успешного reload достаточно закрыть и заново открыть окно плана. Изменения исполнения проверять на следующем запуске готовки: текущая сессия может сохранять старые функции. Подтверждение reload не заменяет проверку поведения в игре.
- Если watcher не запущен, обычная синхронизация через `tools/dev.ps1 -Mod <slug>` сама по себе не обновляет Lua в работающей игре. Сначала использовать штатный workflow из документации мода, не запускать второй watcher на тот же bridge.
- Перезапуск рекомендовать при конкретной необходимости: `RESTART REQUIRED`, добавление/удаление/переименование игрового Lua-модуля, изменения `mod.info`, переводов, scripts или ресурсов; остановка hot reload после ошибки/таймаута; изменения регистрации событий или состояния, которые нельзя надёжно применить через reload. Всегда кратко указывать причину. Правки тестов и документации перезапуска игры не требуют.

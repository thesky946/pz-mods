Источник: `media/scripts/generated/evolvedrecipes.txt:220-254`. Все четыре рецепта имеют `Template = Salad` или `Template = FruitSalad`; у них нет `Cookable = true` и `MinimumWater`, которые явно указаны, например, для супа (`:3-12`) и жаркого (`:135-172`). В установленном `EvolvedRecipe.class` поле `cookable` изначально `false`, а `addItem()` присваивает его результирующей еде. Следовательно, этим рецептам не требуются плита, нагрев и заполнение миски водой.

Проверка в живой игре (`console.txt`, `PLAN: dish=Salad cookware=Base.Bowl recipes=2`) показала, что `getUntranslatedName()` возвращает `Salad` и `FruitSalad`, хотя поле скрипта `Name` содержит `Make Salad` и `Make Fruit Salad`. Первоначальное сопоставление по `Name` находило миску, но ошибочно возвращало `NoCookware`. Для глиняных мисок используется идентификатор рецепта с суффиксом `Clay`, согласованный с именами в скрипте.

`Base.Bowl` и `Base.ClayBowl` — предметы категории Cooking с `FluidContainer`, но сухая миска является основой этих evolved-рецептов. Источник: `media/scripts/generated/items/normal.txt:3763-3786,9602-9625`. Готовые салаты — пища с `ReplaceOnUse = Base.Bowl` / `Base.ClayBowl`; посуда возвращается при употреблении. Источник: `media/scripts/generated/items/food.txt:5681-5721,6326-6358`.

Допустимость ингредиентов определяют декларации `EvolvedRecipe` у самих продуктов и игровая проверка рецепта, а не только категория «овощи/фрукты». Например, `Base.Tomato` содержит `Salad:6`, `Base.Lettuce` содержит `Salad:5`, а `Base.Apple` содержит и `FruitSalad:8`, и `Salad:8`. Источник: `media/scripts/generated/items/food.txt:91-112,8658-8677,14467-14485`. Отдельные записи вида `Salad:...|Cooked` встречаются у ингредиентов (`food.txt:126,211`), поэтому требование предварительной готовки зависит от конкретного продукта. Синтаксис `EvolvedRecipe` и флага `|Cooked` подтверждает также [PZ API Documentation 42.20.4](https://pz-wiki-modding.github.io/PZ-API-Docs/scripts/item.html).

Ванильный `ISAddItemInRecipe:new(character, recipe, baseItem, usedItem)` запускает добавление; `complete()` присваивает `self.baseItem = self.recipe:addItem(...)`. Источник: `media/lua/shared/TimedActions/ISAddItemInRecipe.lua:1-17,66-85,231-243`. Контекстное меню перед действием переносит основу и ингредиент в инвентарь, затем ставит это действие в очередь. Источник: `media/lua/client/ISUI/ISInventoryPaneContextMenu.lua:2372-2391`. В байткоде установленного `projectzomboid.jar`, класс `zombie.scripting.objects.EvolvedRecipe`, `addItem()` при первом добавлении создаёт `ResultItem`, удаляет прежнюю основу из инвентаря и добавляет новый объект; возвращает новый предмет. Значит, идентичность миски после первого ингредиента меняется.

Сигнатуры установленного Java API (`javap -classpath projectzomboid.jar zombie.scripting.objects.EvolvedRecipe zombie.inventory.RecipeManager`): `RecipeManager.getEvolvedRecipe(InventoryItem, IsoGameCharacter, ArrayList<ItemContainer>, boolean)`, `EvolvedRecipe.getItemsCanBeUse(IsoGameCharacter, InventoryItem, ArrayList<ItemContainer>)`, `EvolvedRecipe.addItem(InventoryItem, InventoryItem, IsoGameCharacter) -> InventoryItem`, `getMaxItems() -> int`, `getResultItem() -> String`, `getFullResultItem() -> String`, `isCookable() -> boolean`.

## Приготовленные и замороженные ингредиенты

В `evolvedrecipes.txt:220-254` у всех четырёх салатов отсутствует `AllowFrozenItem`; поле `allowFrozenItem` класса `EvolvedRecipe` по умолчанию `false`. В байткоде установленной игры `EvolvedRecipe.checkItemCanBeUse()` исключает `Food.isFrozen()`, если `allowFrozenItem == false`; ванильное контекстное меню тоже отключает замороженный ингредиент с текстом `ContextMenu_CantAddFrozenFood` (`media/lua/client/ISUI/ISInventoryPaneContextMenu.lua:2036-2040`). Следовательно, обычным ванильным путём замороженный ингредиент нельзя добавить в любой из четырёх салатов; разморозка нужна **до** добавления, поскольку сам салат не проходит нагрев.

Примеры продуктов с обязательной предварительной готовкой: `Base.Potato` (`Salad:9|Cooked`, `food.txt:117-126`), `Base.BaconRashers` (`Salad:4|Cooked`, `food.txt:198-211`), `Base.Egg` (`Salad:7|Cooked`, `food.txt:5416-5426`), `Base.ChickenWings` (`Salad:15|Cooked`, `food.txt:9478-9489`). Точная сигнатура установленной Java-версии: `EvolvedRecipe.needToBeCooked(InventoryItem) -> boolean`. Несмотря на имя, это **проверка допустимости cooked-состояния**, а не «нужно ли готовить». Метод принимает все ингредиенты без `|Cooked` независимо от их cooked-состояния; для ингредиентов с `|Cooked` требует `item:isCooked()` или `item:isBurnt()`, но сгоревшую пищу отдельно отсеивает `getItemsCanBeUse()`. Ванильное меню использует метод для категорий и отключения несовместимого пункта (`ISInventoryPaneContextMenu.lua:2008-2018,2041-2047`). Поэтому готовый картофель, бекон, яйцо и куриные крылышки допустимы для обычного салата, если не нарушены другие условия рецепта. Приготовленный продукт без `|Cooked` (например, `Base.Tomato`, `food.txt:91-110`) также допустим.

Текущее состояние мода: `CookItForMe_Scanner.lua:164` безусловно исключает `isCooked()`, а `CookItForMe_Planner.lua:239,287` повторяет этот запрет. Так мод теряет перечисленные допустимые готовые ингредиенты. Scanner допускает замороженные продукты (`Scanner.lua:155-156`), но салатный рецепт их отвергает. Запись в `recipe:getItemsList()` означает, что тип зарегистрирован ингредиентом; сама по себе она **не проверяет** состояние cooked/frozen, порчу, лимит и текущую миску. `EvolvedRecipe.getItemsCanBeUse()` проверяет заморозку и часть прочих условий, однако не вызывает `needToBeCooked()`; последнюю проверку делает ванильный UI. `ISAddItemInRecipe.isValidStart()` опирается на `getItemsCanBeUse()` (`ISAddItemInRecipe.lua:8-17`), поэтому прямое использование действия без отдельной проверки cooked-флага может принять сырой картофель или мясо вопреки недоступному пункту ванильного меню.

В `EvolvedRecipe.addItem()` нет проверки `isFrozen()` и нет переноса состояния заморозки с ингредиента на результат; новый результат создаётся через `InventoryItemFactory.CreateItem(resultItem)` и для салата помечается `isCookable=false`. Поэтому принудительный прямой вызов `addItem()` может создать внешне готовый салат из замороженного продукта, но это обход ванильной допустимости, а не поддерживаемый сценарий. Для сырого опасного продукта `addItem()` переносит `DangerousUncooked` на результат; такой обход не делает блюдо безопасным. В живой игре эти обходы и употребление результата не проверялись.

## Жидкость в миске и принудительное разрешение заморозки

Обе миски имеют `FluidContainer` (`items/normal.txt:3763-3786,9602-9625`). В установленном `EvolvedRecipe.getItemsCanBeUse()` при `MinimumWater == 0`, отсутствии уже добавленных ингредиентов и `baseItem:getFluidContainer():isEmpty() == false` немедленно возвращается пустой список. Все четыре салата имеют нулевое `MinimumWater`. Значит, миска с водой **или любой иной жидкостью** недопустима как основа салата. `RecipeManager.getEvolvedRecipe(base, player, containers, true)` вызывает `getItemsCanBeUse()` и не показывает такой рецепт; вариант с `false` добавляет рецепт без проверки доступных ингредиентов, поэтому само наличие рецепта в его результате не доказывает пригодность миски. Источник: байткод `projectzomboid.jar`, `zombie.scripting.objects.EvolvedRecipe.getItemsCanBeUse` (offset 57–92), `zombie.inventory.RecipeManager.getEvolvedRecipe` (offset 148–228).

`ISAddItemInRecipe.isValidStart()` проверяет `getItemsCanBeUse()` (`ISAddItemInRecipe.lua:8-17`), поэтому обычное timed action с заполненной миской не стартует. Непосредственный вызов `EvolvedRecipe.addItem()` этой проверки не делает: при первом ингредиенте создаёт новый `ResultItem`, удаляет прежнюю миску из инвентаря и добавляет результат; вызовов копирования или переливания `FluidContainer` в этом методе нет. Таким обходом жидкость теряется вместе с исходной миской. Источник: байткод `EvolvedRecipe.addItem` (offset 15–48,429–445).

Если сторонний код вызовет `recipe:setAllowFrozenItem(true)`, замороженный ингредиент перестаёт отсекаться `getItemsCanBeUse()` и ванильное меню не отключает его по причине заморозки. `EvolvedRecipe.addItem()` не вызывает `Food.setFrozen()` и не копирует время заморозки в созданный результат. `Food.isFrozen()` читает отдельное поле `frozen`, которое у нового объекта из `InventoryItemFactory.CreateItem()` изначально `false`. Поэтому из замороженного **безопасного в сыром виде** продукта вроде `Base.Tomato` получится незамороженный, не требующий нагрева салат; после первого ингредиента это уже предмет пищи с уменьшением голода. У сырого мяса может сохраниться `DangerousUncooked`, поэтому такой результат нельзя считать безопасной пищей. Эти выводы следуют из байткода, без проверки употребления в живой игре.
